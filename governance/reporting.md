# 汇报规范 · Reporting

被问到"进度 / 内容 / 数量"时，我按什么思路汇报。本文件是汇报格式的唯一真源：回答以本文件最新版为准；关联入口见 [`README.md`](../README.md)「五、方法」。

## 0. 元规则（最高优先级）

- **要求调整即自我更新**：用户说"调整 / 优化 / 改一下汇报"时，不许只口头答应——立即更新本文件（edit → 读回验证），再报告一行 diff 摘要。文件没改 = 没记住。
- **证据优先**：任何进度判断必须基于文件证据（文件存在性、mtime、`git log`、文档内 TODO/待确认标记），不凭对话记忆；不确定就明说并去读文件核实。
- **数字不是全部**：统计只是"内容/数量"类问题的第一层，必须附内容层介绍。
- **英文术语必配对照**：文档与汇报中出现的任何英文术语/缩写（含自创记号如 Q/J/R），首次出现处必须带中英文对照表；读者不应需要猜。

## 1. 问"当前研究内容 / 数量"

固定结构（分类表 + 进度 + 说明，不得只报数字）：

1. **总览统计表**：素材 / 观点 / 笔记 / 议题 / 结论 / 项目，各给数量、当前阶段、进度说明；
2. **研究素材表**：按主题标签分类，列出每素材、状态、观点/议题关联、核心内容与下一步；不能只列总数；
3. **观点表**：按研究线或主题分类，列出观点编号、主张、来源素材、当前作用；
4. **议题表**：列出每议题的问题、状态、已形成判断、待验证事项；
5. **结论/产出表**：列出 `research/conclusions/` 结论与 `projects/` 项目，分别说明完成度、回写状态、关联研究；结论为空时必须明确写出；
6. **至少 3 个重点素材/项目简要介绍**：每个 = 核心观点一句话 + 所属研究线 + 当前进度 + 关键文件路径；
7. **缺口与建议表**：列出空主题、未消化素材、未回写结论、待用户决策项，并给出优先级和下一步。

> “所有表”指当前问题涉及的所有内容分类表，不得用一张总表替代分表；若某类为空，也必须保留该表并标注“0 / 空”。
> 规则来源：2026-09-01 问"当前研究数量?"我只报了数字，被用户纠正——只报统计不算汇报；2026-09-07 用户进一步要求所有 table 分类列出，并附进度和相关说明。

## 2. 问某个项目的进度（如"ai-observability 到哪了？"）

思路（按序执行）：

1. **定位**：`projects/<name>/`（工作交付物）或 `topics/` 下对应研究线；先读其 README.md；
2. **盘点**：列出交付文档 + 最近修改时间（`ls -lt` / `git log -- <dir>`），确认"有什么、新到什么程度"；
3. **判进度**：完成 / 进行中 / 阻塞——依据文件内证据（TODO、待二次确认、未决疑问章节）；
4. **汇报五件套**：
   - 一句话定位：这个项目是什么；
   - 交付物清单：N 份文档，列出；
   - 当前状态：完成 X / 进行中 Y / 阻塞 Z，各一句理由 + 文件证据；
   - 未决问题：取自文档"衍生/疑问"或 TODO（最多 3 条）;
   - 建议下一步：一个具体、可立即执行的动作。
5. **引用路径**：关键结论指向具体文件，便于用户点开核验。

## 3. 问总体进度（如"研究进展如何？/ 整体到哪了？"）

思路（按序执行）：

1. **总览统计**：同 §1 的表；
2. **分线推进**：每条活跃研究线一段——现状 + 最近动态（以文件日期/git log 为准）；
3. **跨线连接状态**：观点/议题/结论的数量与质量——议题、结论为 0 本身就是进度信号（收集尚未消化成演化），要点出来；
4. **缺口与建议**：缺什么（空主题、未消化素材、未建议题），给出最值得做的下一步一个。
